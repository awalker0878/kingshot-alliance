# Frontend V3 — Active Governor Context Isolation

## Status

Implemented as a follow-on to the Platform User / Active Governor identity UX contract.

## Architectural invariant

```text
THE PLATFORM USER AUTHENTICATES.
THE ACTIVE GOVERNOR ACTS.
```

A browser may request that one of the authenticated Platform User's owned Governors become active. It may not supply Alliance, Kingdom, membership, rank, role, or capability authority.

## Context fingerprint

Every server-projected Governor identity carries a versioned `contextFingerprint`.

The fingerprint is generated by the server from the resolved identity/security context, including:

- Player reference
- Kingdom reference and number
- active Alliance membership reference
- Alliance reference
- Alliance rank
- specialist role keys
- effective Alliance capabilities

The public fingerprint payload contains only the scope references needed for client isolation plus an opaque hash key:

```text
PlayerContextFingerprint
├─ version
├─ key
├─ playerId
├─ kingdomId
├─ kingdomNumber
├─ allianceId
└─ membershipId
```

The hash key is a cache/state namespace, not an authorization token. Backend authorization remains mandatory for every protected request.

A change to Player, Kingdom, membership, rank, roles, or capabilities changes the fingerprint key and therefore creates a new client context namespace.

## State ownership classes

Frontend state must be explicitly classified.

### Platform state

May survive Governor changes.

Examples:

- locale
- theme
- account preferences
- Platform User presentation settings

Use a Platform-scoped key when persistence is required:

```ts
platformScopedStorageKey('theme')
```

### Player state

Belongs to one Governor but does not necessarily depend on current Alliance membership.

Examples:

- Governor-specific display preferences
- personal filters
- Governor-specific drafts that are intentionally persistent

Use:

```ts
playerScopedStorageKey(playerId, 'preference-name')
```

### Context state

Belongs to the complete resolved Governor / Kingdom / Alliance authority context.

Examples:

- roster data
- Alliance contribution data
- recruitment state
- Kingdom administration state
- King Perks appointment state
- permission-sensitive page data
- polling subscriptions
- realtime subscriptions
- context-bound drafts

Use:

```ts
contextScopedStorageKey(contextFingerprint.key, 'resource-name')
```

Context state must never be reused under a different fingerprint.

## Transition lifecycle

The identity switcher implements the following lifecycle:

```text
PLAYER_SWITCH_REQUESTED
        ↓
OLD_CONTEXT_FROZEN
        ↓
OLD_CONTEXT_ASYNC_WORK_ABORTED / DISPOSED
        ↓
SERVER_ACTIVATION_REQUESTED
        ↓
SERVER VALIDATES PLAYER OWNERSHIP
        ↓
SERVER ESTABLISHES NEW ACTIVE PLAYER
        ↓
SERVER RECONCILES DESTINATION ROUTE
        ↓
NEW CONTEXT RECEIVED
        ↓
OLD CONTEXT INVALIDATED
        ↓
NEW PAGE RENDERED
```

If activation fails:

```text
SERVER ACTIVATION FAILED
        ↓
OLD CONTEXT THAWED
        ↓
CURRENT VALID GOVERNOR REMAINS ACTIVE
```

The previous context's in-flight work is intentionally not allowed to continue through a transition. Components that need to restart work after a failed switch may listen for the thaw event and reload under the still-valid fingerprint.

## Async work registration

`resources/js/identity/context-isolation.ts` provides the common isolation registry.

Context-bound fetches should use a registered `AbortController`:

```ts
const controller = createContextAbortController(contextFingerprint.key);

await fetch(url, {
  signal: controller.signal,
});
```

Long-lived subscriptions, timers, polling loops, and similar resources should register a disposer:

```ts
const unregister = registerContextDisposer(contextFingerprint.key, () => {
  subscription.close();
});
```

The returned `unregister` callback should be called when the component disposes the resource normally.

## Context transition events

The isolation registry emits browser events for components that manage complex local state:

```text
kingshot:context-freeze
kingshot:context-invalidated
kingshot:context-thaw
```

Each event includes the affected fingerprint key in `event.detail.contextKey`.

These events are presentation/runtime coordination only. They do not establish authority.

## Route reconciliation

The browser submits only its current local path as `returnTo` when requesting Player activation.

```text
POST /players/{player}/activate

player = requested owned Player reference
returnTo = non-authoritative current path hint
```

The server activates the target Player first and then applies `PlayerSwitchRouteResolver` to the target context.

### Preserve directly

Stable collection routes can remain selected when valid for the target context, including:

- `/dashboard`
- `/profile`
- `/events`
- `/alliance`
- `/alliance/roster`
- `/alliance/kingdom-alliances`
- `/alliance/contributions`
- `/alliance/transfers`
- `/alliance/content`
- `/alliance/integrations`

### Capability-sensitive preservation

`/alliance/recruitment` is retained only when the new Governor's server-resolved context contains `recruitment.manage`.

If the Governor belongs to an Alliance but lacks that capability, the route falls back to `/alliance`.

### Dynamic/resource-specific routes

Resource-specific URLs are never carried directly into a new identity context.

Examples:

```text
/events/{occurrence}/manage
        ↓
/events

/alliance/roster/dossiers/{player}
        ↓
/alliance/roster

/alliance/recruitment/candidates/{candidate}
        ↓
/alliance/recruitment
```

The safe parent is still subject to the target context policy.

### Unknown or non-local routes

Unknown paths, absolute URLs, protocol-relative URLs, and invalid hints resolve to:

```text
/dashboard
```

This route resolver is a UX policy, not an authorization layer. The redirected request must still pass its normal middleware, policies, capability checks, aggregate authorization, and resource ownership checks.

## Cache rules

Future cache/query libraries must use one of the explicit scope keys.

Do not use:

```text
roster
alliance-roster
/events
recruitment-candidates
```

as globally reusable cache keys.

Use context-qualified keys such as:

```text
context:{fingerprint}:roster
context:{fingerprint}:recruitment-candidates
player:{playerId}:formations
platform:theme
```

A query library may use tuple keys instead of strings, but the complete fingerprint must remain part of every Alliance/Kingdom-sensitive key.

## Mutation rules

A mutation started under one context must not complete as though it belonged to another context.

During a Governor switch:

- prevent additional switches
- freeze old context interaction
- abort or dispose registered old-context asynchronous work
- do not preserve Inertia component state
- do not preserve scroll position
- establish the new context server-side
- reload the reconciled route under the new context

Forms or drafts that intentionally survive must be explicitly Platform-scoped or Player-scoped. Context-bound drafts must never migrate silently between fingerprints.

## Realtime rules

When WebSocket, SSE, or other realtime features are introduced, subscriptions must be registered against the active context fingerprint.

A fingerprint change requires:

```text
unsubscribe old channels
        ↓
clear old callbacks
        ↓
resolve new server context
        ↓
subscribe to new authorized channels
```

Never keep an Alliance or Kingdom subscription alive merely because the URL did not change.

## Acceptance criteria

This slice is complete when:

- the server emits a versioned fingerprint for every owned Governor
- the fingerprint changes with authority-relevant context changes
- the frontend has explicit Platform, Player, and Context persistence key helpers
- context-bound async work can register abort/dispose behavior
- switching freezes the old context before activation
- failed switching thaws the still-valid old context
- successful switching invalidates the old context
- the browser sends no Alliance, Kingdom, membership, rank, role, or capability authority during activation
- route reconciliation is server-owned
- stable valid collection routes can survive a switch
- capability-sensitive routes are evaluated against the target context
- dynamic resource routes collapse to safe parents
- unknown/external route hints fail closed to Command Overview
- backend authorization still independently protects every destination
- automated tests cover the route policy and frontend isolation contract

## Mandatory rule for future UX work

Any new feature that stores, caches, polls, subscribes, or drafts data must declare its scope as one of:

```text
PLATFORM
PLAYER
CONTEXT
```

If the feature cannot clearly classify its state, it is not ready to persist or cache that state.
