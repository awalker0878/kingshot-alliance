# Accounts — Authentication

Status: Current — Architecture V3

Implementation target: `app/Contexts/Accounts/Authentication`

Authentication owns sign-in, sign-out, session establishment and account-confirmation behavior.

Authentication proves which User is operating the application. It does not grant Player-scoped Alliance, Kingdom, Operations or Intelligence authority.

HTTP adapters remain thin and delegate state-changing authentication behavior to capability-owned Actions/services.

RecordAccountSession registers and updates durable browser state within a short current-active account transaction, taking the account lock before session state. This serializes registration with finalization and revocation. Missing/finalized accounts return false, and the conditional update still refuses revoked sessions. Request middleware checks remain useful early rejection, while the owner recheck protects requests already in flight. Primary credential proof freshness during concurrent login/revocation remains tracked separately as HARD-037.

Password confirmation delegates to ConfirmAccountPassword, which locks the current active account and validates its current password before recording confirmation audit. RecentAuthentication session proof is published only after the outermost commit; rollback leaves prior proof unchanged. The callback rechecks account binding, lifecycle and the password fingerprint, suppressing proof if a later operation in that transaction changed the credential or account.

Google reauthentication delegates to ConfirmGoogleAccount after Socialite verifies the response and the Workflow consumes its bound operation. The owner locks the current active account before its Google identity, checks the exact provider subject, and commits identity-use metadata with authentication audit. Subject mismatch records rejection and grants no proof. The outer-commit callback rechecks request binding, active state and that exact identity before publishing Google recent proof.

VerifyAccountPasskey adds the account-first current-active lock boundary around the maintained verifier. Its initial credential lookup only selects the account; maintained validation reselects and locks the exact credential, validates WebAuthn origin/challenge/signature/user verification/user handle/counter, and persists the counter and last-use metadata. PasskeyVerified audit is part of that transaction. Session reference/recent proof publication waits for outer commit and rechecks active account, exact remaining credential and request binding. Guest and non-session verification record their audit without publishing session proof; the verified model is handed directly to login completion without an intermediate session reference.


Password login now delegates to AuthenticateWithPassword. It validates and, when configured, rehashes through the maintained user provider while holding the current active account lock. It captures only immutable fingerprints of authoritative credential, remember-token and MFA state. MFA-enabled password login remains a guest and creates the bounded challenge without a transient authenticated session or remember-token rotation.

CompleteAccountLogin owns password and MFA completion. It rejects an enclosing database transaction, checks current proof and second-factor validity in a short account transaction, then prepares the maintained guard/session rotation outside database locks. A second account transaction rechecks the original proof, consumes a recovery code if selected, initializes a missing remember token, and commits session registration and login audit together. Remember-token preparation is memory-only until this final commit, preserving retry after failures. Login/Authenticated events are buffered by maintained Event.defer until completion succeeds; late event-consumer failures are reported after the durable commit. Failed preparation or completion clears prepared authentication/cookies/recent proof and leaves an unchanged MFA challenge retryable. The ordinary tracking middleware continues checking the registered session marker after the controller.

AuthenticateWithGoogle captures current active account and exact Socialite-verified provider subject under account/identity locks with provider-use metadata. It routes through the same MFA challenge and completion owner. Both Google and password registration auto-login use current credential verification after onboarding commits; password registration also pins the expected newly created account ID. The obsolete Workflow login/audit sequence, detached MFA lookup and query authority are removed. Google connection uses the current-identity confirmation owner before fresh proof is published. AccountPasskeyLoginController retains maintained options, request validation, assertion verification and login policy while handing the verified credential directly to CompleteAccountLogin. The response now only presents HTML/JSON redirect; the intermediate passkey-reference session field is removed. User-verifying passkeys satisfy MFA without consuming a recovery code. User exposes the maintained guard password contract as a string for password-less remembered-cookie hashing; password eligibility still uses the explicit stored-credential policy. Logout remains tracked under HARD-037.


Passkey account adapters translate known WebAuthn ceremony/counter rejections at the maintained validation seam into InvalidPasskeyException credential feedback. They do not catch operational or database failures as input errors; owner rollback behavior remains intact.

RestoreAccountSession owns remembered-session admission. TrackAccountSession is ordered immediately after StartSession, before authentication, throttling and bindings resolve the user. The maintained guard validates the recaller and rotates raw storage without an enclosing database transaction; the owner then locks the current account, compares the verified snapshot against existing credential/remember/MFA state, and commits session registration with login audit. Login/Authenticated events remain deferred until admission succeeds. Invalid or failed restoration abandons prepared authentication and cookies without retrying failing raw destruction. Restored browsers receive no fresh credential proof, and stale recent-authentication/MFA challenge state is cleared. Ordinary following requests update the existing durable session marker without another login audit.
