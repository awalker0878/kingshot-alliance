# ADR NNNN — Decision title

- **Status:** Proposed
- **Date:** YYYY-MM-DD
- **Owners:** Name or role
- **Related scope:** Phase N, named increment, or program concern
- **Supersedes:** None or ADR NNNN

Allowed status values are `Proposed`, `Accepted`, `Superseded`, or `Rejected` as defined by the [architecture and program-governance standard](../product/architecture-governance-standard.md).

## Context

Describe the forces, constraints, risks, current architecture, and alternatives that make a durable decision necessary.

## Decision

State the decision precisely enough to guide implementation and review. An ADR may refine architecture but must not silently approve new product scope.

## Consequences

### Positive

- Outcome

### Negative or trade-off

- Cost or constraint

## Supported boundaries affected

Identify domains, shared runtime, external boundaries, or documentation contracts whose direction/ownership changes. Link the owning contracts rather than copying their implementation detail.

## Validation

Describe the tests, metrics, review, evidence, or experiment that confirms the decision is implemented and remains appropriate.

## Revisit when

List conditions that should trigger reconsideration.

## Supersession handling

If this ADR replaces an accepted ADR, name it in `Supersedes`. After acceptance, change the older ADR status to `Superseded` and link it to this replacement. Preserve the older rationale as historical decision evidence rather than rewriting it.
